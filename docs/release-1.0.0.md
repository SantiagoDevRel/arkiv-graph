## Review correction: bounded sample retry

The browser sample retains both transaction hashes, stable sample identifiers, gas/nonce/receipt metadata and available created keys. SDK success and its hash are persisted as terminal before any follow-up receipt lookup. Null/uncertain or disagreeing receipts return typed `SampleConfirmationError` outcomes (`CONFIRMATION_PENDING` / `RECEIPT_DISAGREES`) with retained transaction links and cannot downgrade that success or authorize another send, including after a new call. It authorizes only one retry when the SDK itself reports a confirmed revert and a corroborating receipt proves gas usage equals the canonical transaction's gas limit. A timeout or unrelated SDK error cannot authorize a retry. The retry re-estimates at `latest`, reads a fresh latest nonce and uses at least twice the previous gas while remaining below half the head gas limit. Semantic reverts, null/uncertain receipts, signature rejection, success and a second exhausted revert cannot authorize another send. Tests cover all of these cases, replay across calls after clearing the legacy hash marker, and an oversized retry budget. Core has no signing helper; the separate maintainer seeder does not automatically retry.

The modified exported app flow also passed a real Node EIP-1193 local-signer control: it [created an isolated sample](https://rabdi.explorer.arkiv.network/tx/0x4102b5a010bbf231db5b7483e800c1ef4f908bb0b89fc4e3e3c34070027bea4e), retained all created keys, deleted only those disposable entities and refused another send after the successful sample disappeared from queries. GasUsed 6,737,893 versus gasLimit 13,585,072 verified double headroom. The public social sample was untouched. Exhausted/semantic/null/rejection outcomes are mocked evidence; this live control did not deliberately exhaust gas or exercise a browser extension.
